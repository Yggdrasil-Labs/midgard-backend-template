# 文档与文件治理

本规范约束文档、工具和过程产物的归属。Java 分层、对象流与类名继续以 [ARCHITECTURE](../../ARCHITECTURE.md) 为准；日常步骤见[开发指南](../engineering/development.md)。

## 内容归属

| 位置 | 维护内容 |
| --- | --- |
| 根 README、实际需要的模块 README | 使用方式、配置、示例、能力与限制 |
| AGENTS、[文档总索引](../index.md) | 硬约束摘要与阅读地图，不复制专题全文 |
| ARCHITECTURE、[领域说明](../DOMAINS.md) | 稳定分层边界与实际领域落点 |
| `docs/design-docs/` | 实际架构设计、跨需求的关键技术取舍及其适用边界 |
| `docs/standards/` | 长期规范、工程原则；已有安全、可靠性规则继续在原页面维护 |
| `docs/engineering/` | 开发与维护操作步骤，不复制约束正文 |
| `docs/active/index.md` | 活跃版本及其记录入口 |
| `docs/active/tech-debt-tracker.md` | 跨版本的问题、证据、实施关联与关闭依据 |
| `docs/active/{version}/release.md` | 版本目标、需求清单、交付状态和最终验证结果 |
| `docs/active/{version}/{requirement}/` | 版本内需求的计划及按需增加的需求、设计说明 |
| `docs/archive/{version}/` | 整体归档的版本记录，不能作为当前行为承诺 |
| `docs/generated/`（有实际产物时再建立） | 可复现生成的参考文档，登记实际来源 |

同一易变事实只在一个位置维护，其他页面通过链接引用。依赖和插件版本以 POM 为事实来源，普通说明不重复版本清单；必要技术基线、兼容性说明及历史证据可保留版本号。

## 新增文件准入

新增前先说明读者或调用方、持续用途和唯一维护位置；能更新现有页面或实现时，优先更新原位置。

- 根目录 Markdown 默认仅保留 README、AGENTS、ARCHITECTURE、CHANGELOG 及必要许可证文件；专题说明进入 `docs/`。
- 新增文档和需求目录采用语义明确的 `kebab-case` 名称。架构 RFC 使用 `arch-<主题>.md`；已有有效路径不为统一大小写机械搬迁。
- 不预建空目录、空索引或只有模板文字的页面。需要独立检索多项内容时才增加索引。
- 一次性排查脚本、探针、原始日志、有效 POM、临时 fixture 和运行报告放系统临时目录或已有构建输出目录，不进入版本控制。需要长期追溯的交付结论写入版本记录，问题证据写入技术债清单。
- 若新增 `scripts/`、`tools/` 或扩展已有脚本，须在变更说明中写清长期职责、实际复用入口与持续维护理由。仅改名、参数化、重复调用或包装为通用函数，不能使专项脚本成为公共工具；不把一次性逻辑嵌入已有脚本规避此规则。
- 业务回归测试及必要资源归所属模块的 `src/test/`；生成 Java、编译产物和运行日志不作为源码提交。凭据只使用本地配置或受控注入，示例使用占位值。

## 按任务选择文档

- 局部文字、事实与链接修订直接更新对应页面并验证。
- 多文件能力变更、公开契约调整、结构调整或重构，在已确认版本的需求目录中形成 `plan.md`；小需求可只保留计划，复杂的需求契约和技术取舍按需增加 `spec.md`、`design.md`。
- 无需独立计划的局部代码修复，在所属版本的 `release.md` 中登记独立交付，不为凑文件集合创建需求目录。
- 跨需求的架构决策进入 `docs/design-docs/`；文档组织和协作规则直接维护本规范与开发指南。日常治理的讨论、修改原因和检查结果在会话中说明，不另建治理 RFC。
- 单纯分析或登记问题使用会话和技术债清单，不自动创建需求目录或进入实施。

## 版本与需求

### 版本归属

业务需求、技术债实施和代码交付先明确归属版本。优先使用用户指定的版本；已有确认过的版本分支或活跃版本上下文可以沿用。版本未确定、存在多个候选或来源冲突时，先讨论归属，再建立版本目录。

版本目录采用三段 semver，如 `1.3.0`；Git tag 的 `v` 前缀不进入目录名，需求名使用 kebab-case。POM 中的构建版本、已发布标签和目标交付版本分别核对，不据此擅自修改版本或创建分支。

```text
docs/active/
  index.md
  tech-debt-tracker.md
  {version}/
    release.md
    {requirement}/
      plan.md
      spec.md       # 按需
      design.md     # 按需
```

确认版本和实际交付范围后才建立记录，不预建空版本。需要需求文档时，不使用无版本的 `docs/active/{requirement}/` 目录。长期规范及其维护直接归属规范文件，无需为文档治理推测一个业务版本。

### 需求文档的职责

| 文档 | 维护内容 |
| --- | --- |
| `spec.md` | 需求目标、行为和接口/数据契约、验收标准 |
| `design.md` | 实现方案、必要取舍、影响范围与兼容性 |
| `plan.md` | 实施范围、关键决策、任务步骤及文件、验证方式和决策边界 |

计划作为静态实施依据，方案变化时修订；执行进度通过会话或任务工具交流，最终状态和验证结果集中写入版本记录，不在计划、索引和多份报告中重复维护。

### 版本记录的最小格式

每个版本只维护一份 `release.md`，包含以下内容：

| 部分 | 必要内容 |
| --- | --- |
| 版本摘要 | 版本号、目标、范围及当前版本状态；实际发布后才填写发布日期 |
| 需求交付 | 需求名称、相对路径、简述及交付状态；技术债实施关联原 TD 编号 |
| 独立交付 | 无需需求目录的局部修改、实际范围及交付状态 |
| 最终验证摘要 | 对应交付项、验证对象与环境、命令和结果、未覆盖内容 |
| 风险与遗留债务 | 未解决事项、关联技术债；风险接受须有明确决定及其来源 |

交付状态必须区分已实现、验证通过和待验收。失败、跳过及环境阻塞如实记录，不能以提交存在或 PR 合并代替验证。未提交时如实标明未提交，不为填写记录创建提交。单独证据文档只有在确有持续检索需要时建立，并由版本记录链接。

## 技术债流转

- 技术债清单保持跨版本台账，保留原 ID、问题证据、影响和关闭条件；登记或确认优先级不代表授权修复。
- 确定实施后，按版本归属规则关联实际需求或独立交付，并从技术债条目指向该入口。
- 按关闭条件核对结果，保留关闭日期及证据。只完成源码修改但集成验收未运行时，记录已完成部分和待验收内容，不能直接关闭。
- 暂停或变更方向时，报告已有差异与未完成事项，由明确的范围和授权决定保留、隔离或撤回，不混入后续任务。

## 事实与更新纪律

使用说明和规范维护当前有效状态，过程说明留在需求或归档。当前实现以源码、配置和实际验证为据；实现违反约束时记录偏差，不静默放宽规则。

新增或下线业务能力、修改公共契约、配置语义或文件位置时，只同步受影响的说明与导航。必须区分已实现、预留、建议和待验证；目录、注释、测试源码存在，不等于能力或测试已运行通过。

迁移文件时先确定内容归属，再修改当前引用，最后删除重复页面。历史正文保留原意，可修复断链与错误位置；不把历史命令或验收结果改写成当前事实。归档、提交和发布分别核验，不能相互代替。

## 版本归档

用户确认归档后，将完整版本目录从 `docs/active/{version}/` 移入 `docs/archive/{version}/`，同步两个索引和相对链接；同一版本的需求、交付记录和证据保持在一起。

以“已完成”归档前，核对版本范围、全部交付和最终验证摘要，未解决事项转入技术债或后续版本，或记录用户明确接受的风险。开发完成不等于发布完成，真实发布前不填发布日期或标记已发布。

停止、取消的版本如需归档，记录原因和未完成项，不能标成已完成。归档保留原意，不补造版本和验收结论。保留期限用于巡检提醒，删除历史资料另按明确授权执行。

## 生成文档

实际产物在文档总索引或所属模块登记路径、数据源、生成方式和生成时间；多项产物确需独立检索时，再建立人工维护的生成文档索引。当前没有生成产物，不保留空目录、占位索引或虚构时间；未实现的生成需求登记到技术债。

生成正文不手改。源数据或生成方式变化时重新生成，生成器缺失或数据源未确定时保留缺口，不复制一个长期漂移的手写版本。内容是否过期以输入变化为依据，日期用于辅助检查。

## 文档验收

按本次差异检查 Markdown 结构、内部链接与锚点、索引可达性、重复事实和源文件是否存在，并执行 `git diff --check`。自动检查只能证明其覆盖的规则，语义与实现状态仍需人工核对。

只报告实际执行的检查及其范围；未执行项和已有无关问题单列。纯文档修改无需运行 Java 全量构建。本规范不声明仓库已经具备自动检查工具。
