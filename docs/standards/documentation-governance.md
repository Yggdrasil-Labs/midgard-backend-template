# 文档与文件治理

本规范约束文档、工具和过程产物的归属。Java 分层、对象流与类名继续以 [ARCHITECTURE](../../ARCHITECTURE.md) 为准；日常步骤见[开发指南](../engineering/development.md)。

## 内容归属

| 位置 | 维护内容 |
| --- | --- |
| 根 README、实际需要的模块 README | 使用方式、配置、示例、能力与限制 |
| AGENTS、[文档总索引](../index.md) | 硬约束摘要与阅读地图，不复制专题全文 |
| ARCHITECTURE、[领域说明](../DOMAINS.md) | 稳定分层边界与实际领域落点 |
| `docs/design-docs/` | 长期设计、方案取舍与架构 RFC；已有工程信条保留原路径 |
| `docs/standards/` | 新增的长期规范；已有安全、可靠性规则继续在原页面维护 |
| `docs/engineering/` | 开发与维护操作步骤，不复制约束正文 |
| `docs/active/` | 当前需求、计划、验收摘要和技术债 |
| `docs/archive/` | 历史过程与证据，不能作为当前行为承诺 |
| `docs/generated/`（有实际产物时再建立） | 可复现生成的参考文档，登记实际来源 |

同一易变事实只在一个位置维护，其他页面通过链接引用。依赖和插件版本以 POM 为事实来源，普通说明不重复版本清单；必要技术基线、兼容性说明及历史证据可保留版本号。

## 新增文件准入

新增前先说明读者或调用方、持续用途和唯一维护位置；能更新现有页面或实现时，优先更新原位置。

- 根目录 Markdown 默认仅保留 README、AGENTS、ARCHITECTURE、CHANGELOG 及必要许可证文件；专题说明进入 `docs/`。
- 新增文档和需求目录采用语义明确的 `kebab-case` 名称。架构 RFC 使用 `arch-<主题>.md`；已有有效路径不为统一大小写机械搬迁。
- 不预建空目录、空索引或只有模板文字的页面。需要独立检索多项内容时才增加索引。
- 一次性排查脚本、探针、原始日志、有效 POM、临时 fixture 和运行报告放系统临时目录或已有构建输出目录，不进入版本控制。需要长期追溯的结论摘要写回已有计划或技术债。
- 若新增 `scripts/`、`tools/` 或扩展已有脚本，须在变更说明中写清长期职责、实际复用入口与持续维护理由。仅改名、参数化、重复调用或包装为通用函数，不能使专项脚本成为公共工具；不把一次性逻辑嵌入已有脚本规避此规则。
- 业务回归测试及必要资源归所属模块的 `src/test/`；生成 Java、编译产物和运行日志不作为源码提交。凭据只使用本地配置或受控注入，示例使用占位值。

## 按任务选择文档

- 局部文字、事实与链接修订直接更新对应页面并验证。
- 多文件能力变更、结构调整或重构先在 `docs/active/{需求}/plan.md` 记录目标、范围、顺序和验收要求；行为或方案复杂时再增加 spec、design。
- 实质性改变系统边界、依赖方向或长期原则，先在设计目录记录 RFC 的背景、取舍和授权依据；事实维护无需另建 RFC。
- 验收摘要优先记录在已有计划，证据确需独立阅读时再增加 verification。任务事实由需求记录维护，索引只保留必要摘要，不另建重复的进度表或编号表。
- 单纯登记问题使用现有技术债清单；登记、规划、实现和验证是不同状态，不因文档存在就视为完成。

## 事实与更新纪律

使用说明和规范维护当前有效状态，过程说明留在需求或归档。当前实现以源码、配置和实际验证为据；实现违反约束时记录偏差，不静默放宽规则。

新增或下线业务能力、修改公共契约、配置语义或文件位置时，只同步受影响的说明与导航。必须区分已实现、预留、建议和待验证；目录、注释、测试源码存在，不等于能力或测试已运行通过。

迁移文件时先确定内容归属，再修改当前引用，最后删除重复页面。历史正文保留原意，可修复断链与错误位置；不把历史命令或验收结果改写成当前事实。归档、提交和发布分别核验，不能相互代替。

以“已完成”归档计划前，应确认主要目标已完成、关键验证已执行、未解决事项已转入技术债或后续计划。仅为迁移旧资料而归档时，保留其原状态，不自动标记完成。

## 生成文档

实际产物在文档总索引或所属模块登记路径、数据源、生成方式和生成时间；多项产物确需独立检索时，再建立人工维护的生成文档索引。当前没有生成产物，不保留空目录、占位索引或虚构时间；未实现的生成需求登记到技术债。

生成正文不手改。源数据或生成方式变化时重新生成，生成器缺失或数据源未确定时保留缺口，不复制一个长期漂移的手写版本。内容是否过期以输入变化为依据，日期用于辅助检查。

## 文档验收

按本次差异检查 Markdown 结构、内部链接与锚点、索引可达性、重复事实和源文件是否存在，并执行 `git diff --check`。自动检查只能证明其覆盖的规则，语义与实现状态仍需人工核对。

只报告实际执行的检查及其范围；未执行项和已有无关问题单列。纯文档修改无需运行 Java 全量构建。本规范不声明仓库已经具备自动检查工具。
